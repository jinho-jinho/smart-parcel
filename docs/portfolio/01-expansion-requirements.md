# 확장 요구사항과 검증 규모

수치는 실제 운영 실적이 아닌 소형·임시 군수/구호 분류 현장을 가정한 시험 조건이다.
팀 프로젝트 이후 박진호의 Java/Spring 백엔드 고도화 범위로 관리한다.

## 이번 구현 범위

1. 조직에 사용자와 여러 벨트가 소속된다. 조직 소속은 인증된 사용자/장비에서 결정한다.
2. 벨트마다 장비, 슈트, 활성 설정을 분리한다. 활성 제어 장비는 벨트당 최대 1대다.
3. 배포 버전에 규칙, 우선순위, 그룹명, 슈트명과 서보 각도를 고정한다.
4. 배포 버전은 수정하지 않는다. 서버 지정 버전과 장비 적용 버전을 별도로 기록한다.
5. 장비 키로 설정 조회·판정·배출 확인·장비 오류를 전송한다.
6. attemptId는 분류 시도, eventId는 그 시도에서 발생한 개별 사건이다.
7. 판정과 배출 확인을 구분한다. 동일 이벤트 재전송은 상태·알림을 중복 반영하지 않는다.
8. 시뮬레이터는 이미지와 이벤트를 SQLite에 저장하고 서버 저장 완료 응답 뒤 ACKED로 바꾼다.
9. 기존 이력은 보존한다. 알 수 없는 과거 장비·버전을 추측해 생성하지 않는다.

v1은 DECISION 수신 시 시도를 생성한다. 통계 분모는 서버에 판정이 저장된 시도 수다.
판정 전에 정지한 물품까지 포함한 전체 물리적 투입 수를 뜻하지 않는다.
후속 배출 이벤트는 판정 저장 응답 이후 전송한다. 임의 도착 순서를 수용하는 Inbox는 이번 범위가 아니다.

## 부하 가정

| 시나리오 | 벨트 | 벨트당 간격 | 기본 판정 이벤트 | 운영자 조회 |
| --- | ---: | ---: | ---: | ---: |
| 단일 조직 | 5 | 10초 | 0.5/s | 별도 |
| 기본 목표 | 10개 조직 × 5 = 50 | 10초 | 5/s | 20명 × 2 API / 10초 = 4/s |
| 확장 | 20개 조직 × 5 = 100 | 5초 | 20/s | 50명 × 2 API / 10초 = 10/s |
| 집중 조회 | 100 | 5초 | 20/s | 50명 × 4 API / 5초 = 40/s |

물품 수, 이벤트 수, HTTP 재시도 수, DB 쓰기 횟수는 다른 지표다.
배출 확인을 물품마다 추가하면 20물품/s는 판정 20 + 배출 20 = 40이벤트/s가 된다.
오류와 재전송, 설정 조회는 별도다.

하루 8시간 기준 기본 목표에서 144,000개 시도, 30가동일에 432만 건이 누적된다.
조회 실험은 10만 → 100만 → 1,000만 건으로 확장한다.
현재 복합 인덱스는 신규 기준 상태에 포함된다. 이후 동일 API·데이터·환경에서 변경한 효과만 비교한다.

## 후속 실험 목표 — 아직 달성 수치 아님

- 기본 부하에서 이미지 제외 판정 저장 p95 500ms, 이력 50건 p95 500ms, 통계 p95 1초.
- 100벨트의 판정만 20/s일 때 10분 단절 → 12,000건 적체.
- 신규 20/s를 유지하며 5분 내 복구하려면 적체 처리 40/s를 추가한 평균 60건/s 이상이 필요.
- 이미지 크기·첨부 비율을 별도로 고정한다. 현재 구현은 이미지까지 DB 트랜잭션에 저장한다.
- 생성/저장 ID 차이, 중복 반영, 대기/격리 건수로 복구를 검증한다.
- 이번 검증은 기능·무결성·동시성 시험이다. 위 성능 실험은 아직 수행하지 않았다.
